| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | Функциональные (Functionality)     |              |
| F1  | Клиент сайта видит список депозитов с актуальными ставками и может подать заявку (ФИО, телефон) | MVP, минимальный рабочий функционал для новых клиентов |
| F2  | Клиент интернет-банка видит список депозитов с персональными ставками, может выбрать счет и сумму, подать заявку | Необходима авторизация в интернет-банке |
| F3  | Сотрудники бэк-офиса могут работать с заявками на депозиты | Требуется интеграция с АБС/CRM |
| F4  | Менеджер колл-центра может видеть заявки сайта, звонить клиенту, предлагать спецусловия | Важно для конверсии новых клиентов |
| F5  | Подтверждение заявки на депозит через СМС-код для клиентов интернет-банка | Реализовать без доработок ядра СМС |
| F6  | СМС-уведомления о подтверждении ставки и открытии депозита | Обеспечить информирование клиента |
| F7  | Загрузка и редактирование ставок по депозитам из XLS для бэк-офиса депозитов и кредитов | Возможно временное решение до автоматизации в АБС |
| F8  | Передача данных (заявки) в систему для обработки менеджером | Разделение потоков новых и существующих клиентов |
|     |                                    |              |
| U   | Удобство использования (Usability) |              |
| U1  | Интерфейс соответствует дизайн-системе банка (цвета, элементы, брендинг) | Важно для узнаваемости и лояльности клиентов |
| U2  | Максимально простой и понятный процесс подачи заявки на сайте и в интернет-банке | Снижение числа отказов и ошибок |
| U3  | Быстрый отклик интерфейса (отклик операций — миллисекунды) | Особенно важно для MVP и клиентского опыта |
|     |                                    |              |
| R   | Надёжность (Reliability)           |              |
| R1  | Сервисы должны работать 24/7, обеспечивая доступность не ниже 99,9%. Это требование к SLA для критичных систем. | Требование к SLA для критичных систем |
| R2  | В случае сбоя в ЦОД возможен переход на резервный ЦОД | Обеспечение непрерывности бизнеса |
| R3  | Минимизация влияния сбоя интернет-банка на работу других систем | Важно для устойчивости банка в целом |
| R4  | Все данные клиентов (включая трафик и заявки) должны передаваться только в зашифрованном виде с использованием протокола TLS версии не ниже | Критично для завершения бизнес-процессов |
|     |                                    |              |
| P   | Производительность (Performance)   |              |
| P1  | Отклик по операциям (загрузка справочников, расчет ставок) не превышает 1 сек. | Устранение текущих проблем с производительностью |
| P2  | Возможность горизонтального масштабирования сервисов интернет-банка | Для обеспечения роста нагрузки и доступности |
| P3  | Вертикальное масштабирование для АБС (ограничение платформы) | Необходимо учитывать при проектировании архитектуры |
|     |                                    |              |
| S   | Поддерживаемость (Supportability)  |              |
| S1  | Документирование решений и API для дальнейшего расширения | Важно для развития продукта |
| S2  | Использование технологий с экспертизой внутри банка (MS SQL, Oracle, поддерживаемые языки) | Снижает риски внедрения и поддержки |
| S3  | Возможность интеграции с очередями сообщений (Kafka — на перспективу) | Для будущей микросервисной архитектуры |
| S4  | Совместимость новых решений с текущими платформами | Обеспечивает бесшовную интеграцию |
|     |                                    |              |
| +R  | + Ограничения (Restrictions)       |              |
| +R1 | Прямая работа интернет-банка с API АБС запрещена для новой функции | Не допустить перегрузки АБС и рисков для банка |
| +R2 | Использование только технологий, совместимых с существующими платформами | Минимизация рисков и затрат на внедрение |
| +R3 | Защита всех данных клиентов (трафик, заявки) с помощью шифрования | Соответствие требованиям ИБ и законам |
| +R4 | Операции с СМС реализуются силами команды банка, без доработок ядра | Снижение времени и стоимости реализации |
| +R5 | Приоритет использования существующих решений, новых — только при необходимости | Снижение технического долга и рисков внедрения |
| +R6 | Масштабирование АБС только вертикальное из-за ограничений СУБД | Учитывать при проектировании нагрузки |
