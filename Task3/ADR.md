**<a name="_qmphm5d6rvi3"></a>Решение**

**Диаграммы см. в директории:**

- `C1_Context_Diagram.puml` — диаграмма контекста
- `C2_Container_Diagram.puml` — диаграмма контейнеров (детализация интернет-банка и АБС)

**Описание компонентов и интеграций:**

- Основной пользовательский поток реализован через сайт и интернет-банк.
- Для новых клиентов заявки с сайта уходят в систему колл-центра (микросервисы подрядчика, React/Java Spring Boot/PostgreSQL).
- В интернет-банке (ASP.NET MVC 4.5, MS SQL, монолит) реализуется подача заявки и подтверждение по СМС (через шлюз).
- Для обработки заявок бэк-офис использует существующую АБС (Delphi-клиент, Oracle, PL/SQL).
- Работа со ставками (временно) — через XLS-файлы, далее через АБС.
- Система уведомлений/СМС — шлюз телеком-оператора, поддерживается внутренней IT-командой.

**Логика выбора технологий:**
Везде используются платформы и стек, для которых есть экспертиза. Новые интеграции минимальны, максимальный приоритет повторному использованию существующих компонентов (например, шлюз СМС, текущий интернет-банк, существующая система колл-центра).

**<a name="_bjrr7veeh80c"></a>Альтернативы**

**Вариант 1:** Прямая интеграция интернет-банка с АБС
Недостатки: угроза нагрузке на АБС, риски для отказоустойчивости, невозможность горизонтального масштабирования.

**Вариант 2:** Весь процесс через ручную обработку в CRM/колл-центре
Недостатки: Низкая автоматизация, плохой клиентский опыт, высокая трудоёмкость.

**Вариант 3:** Использование новых внешних облачных сервисов
Недостатки: Риски по безопасности, отсутствие экспертизы, сложность поддержки.

**Недостатки, ограничения, риски**

- Перегрузка АБС: часть операций все равно ложится на АБС, возможны задержки.
- Сложность интеграции: нужны новые сервисы/интерфейсы, часть из которых создаются с нуля.
- Ограничения масштабирования: АБС масштабируется только вертикально.
- Временное использование XLS для ставок: риск ошибок, требует доработки на будущее.
- Безопасность: требуется регулярный аудит передачи данных и шифрования.
